1.1  TYPES OF CODING ROUNDS
==============================================================================

 FORMAT                  TYPICAL TIME     WHAT IS EVALUATED

 INTERVIEWERS WATCH FOR
   1. Do you clarify before coding?         4. Is your code correct and clean?
   2. Do you reason about trade-offs?       5. Do you test it yourself?
   3. Can you improve a brute force?        6. Can you state complexity precisely?

 DIFFICULTY vs TIME (target speeds when prepared)
   Easy   : 10-15 minutes (including testing)
   Medium : 20-30 minutes   <- the bulk of interviews
   Hard   : 35-45 minutes (or discuss approach + partial code)
   A 45-minute interview usually means ONE medium + a follow-up, or TWO easy-
   mediums.

          |---------|---------|---------|-------------------|--------|----|
          | 1.Under-| 2.Examples| 3.Brute | 4. CODE the       | 5.TEST | 6. |

          | clarify | (pattern) | optimise|                   |        | up  |

  RULE OF THUMB: spend about 1/3 of the time THINKING and TALKING (before the

     85-90 re-run samples, re-check edge cases, final submissions

  ALARM CLOCKS: if you have no approach after ~10 minutes, ask for a hint (live

  simplify: finish a correct brute force, then narrate the optimisation.

==============================================================================
1.3  THE FRAMEWORK
==============================================================================

 UMPIRE (a widely taught structure)
    U  UNDERSTAND   restate the problem, clarify inputs/outputs/constraints
    M  MATCH        which pattern / data structure does it resemble?
    P  PLAN         outline the algorithm in plain steps (pseudocode)
    I  IMPLEMENT    write clean Python
    R  REVIEW       dry-run with an example; test edge cases; fix bugs
    E  EVALUATE     time & space complexity; trade-offs; alternative solutions

 THE 7-STEP VERSION (use it every time)
    1) READ the problem twice. Underline input, output, constraints.
    2) CLARIFY with questions (see 1.4). Write down assumptions.
    3) WORK AN EXAMPLE by hand (a small one, then an edge case). Often the
       pattern appears when you do it manually.
    4) BRUTE FORCE: state it in one or two sentences with its complexity. This
       shows you can solve it and gives a baseline. Do not code it unless asked
       (or unless it is your safety net in an OA).
    5) OPTIMISE: find the bottleneck (repeated work? a search? sorting?) and
       apply a technique (hash map, two pointers, window, heap, DP, binary
       search ...). State the new complexity. Get the interviewer's OK.
    6) CODE: top-down, meaningful names, small helper functions, no premature
       cleverness. Talk while you type.
    7) TEST: walk through your own code with the example, then edge cases.
       State final time and space complexity.

 FLOW DIAGRAM
    problem -> clarify -> example -> brute force (complexity)
                                         |
                       bottleneck? -> pick technique -> better complexity
                                         |
                              agree plan -> code -> dry run -> edge cases
                                         |
                                  complexity + follow-ups

==============================================================================
1.4  CLARIFYING QUESTIONS CHECKLIST
==============================================================================

 INPUT
   - Type and range of values? Negative numbers? Zeros? Floats?
   - Size of n? (decides the target complexity)
   - Can the input be empty / null? A single element?
   - Sorted? Duplicates allowed? Distinct values?
   - Characters: lowercase only? ASCII/Unicode? Case sensitive? Spaces?
   - Graph: directed? weighted? cycles? connected? nodes numbered 0..n-1?
   - Is the input modifiable (in place) or must it be preserved?
 OUTPUT
   - Return values or indices? All solutions or any one? Sorted order needed?
   - What if no answer exists (-1, None, empty list)?
   - Multiple valid answers - is any accepted? Ties?
 CONSTRAINTS
   - Time/space limits? Is O(n) extra space allowed? In-place required?
   - Called once or many times (precompute vs per-query cost)?
   - Streaming data? Fits in memory?
 CORRECTNESS
   - Overflow concerns (irrelevant in Python but mention for other languages).
   - Can I assume valid input?
 Say your assumptions out loud: "I'll assume the array is non-empty, otherwise
 return 0."

==============================================================================
1.5  CONSTRAINTS -> REQUIRED COMPLEXITY
==============================================================================

 Read n (and other limits) FIRST. The constraint tells you what is intended.
 Rough budget: C++/Java ~10^8-10^9 simple operations per second;
 CPYTHON ONLY ~10^7 simple operations per second (pure loops).
 For Python, aim 5-10x lower than C++ limits, and push work into built-ins
 (sorted, sum, set, dict, Counter, heapq, bisect, itertools) which run at C speed.

   n (max)          Target complexity         Typical techniques
   ---------------  ------------------------  ----------------------------------
   n <= 10          O(n!)  O(n * n!)          permutations, brute force
   n <= 20-25       O(2^n) O(n * 2^n)         subsets, bitmask, meet-in-the-middle
   n <= 40          O(2^(n/2))                meet in the middle
   n <= 100         O(n^4)                    nested loops, small DP
   n <= 400-500     O(n^3)                    Floyd-Warshall, interval DP
   n <= 2,000-5,000 O(n^2)                    2D DP, pair enumeration (Python: 2000)
   n <= 10^5-2*10^5 O(n log n)                sort, heap, binary search, DSU, segment tree
   n <= 10^6        O(n) / O(n log n) light   hash map, two pointers, sliding window, prefix sums
   n <= 10^7-10^8   O(n) tight                counting, sieve, math, no heavy structures
   n <= 10^9-10^18  O(log n) / O(sqrt n)/O(1) binary search, fast power, math, bit tricks
   Strings length 10^5  O(n) / O(n log n)     KMP, hashing, window, trie
   # HOW the table is derived: allowed operations = time limit x speed (about 1 s x 10^7 steps in Python). Choose the largest n with f(n) <= 10^7..10^8:
   #   n^2 <= 10^7 -> n ~ 3000 | n log2 n <= 10^7 -> n ~ 5*10^5 (5*10^5 x 19 = 9.5*10^6) | n^3 <= 10^8 -> n ~ 460 | 2^n <= 10^7 -> n ~ 23 | n! <= 10^7 -> n ~ 10.

 DIAGRAM: how complexity grows with n = 10^5
      O(1)        1
      O(log n)    17
      O(sqrt n)   316
      O(n)        100,000
      O(n log n)  1,700,000          <- fine in Python
      O(n^2)      10,000,000,000     <- TOO SLOW (needs ~1000 s in Python)
      O(2^n)      impossible
   # HOW (n = 10^5): log2(10^5) = 16.6 -> 17. sqrt(10^5) = 316. n log n = 10^5 x 17 = 1.7*10^6. n^2 = 10^5 x 10^5 = 10^10 steps;
   #      at 10^7 steps per second that is 10^10 / 10^7 = 1000 seconds.

 IF YOUR IDEA IS TOO SLOW: look at which loop/search is the bottleneck.
   nested loop to find a partner       -> hash map or sort + two pointers
   repeated range sums                 -> prefix sums
   repeated min/max over a window      -> monotonic deque / heap
   repeated "is it present?"           -> set
   repeated sorting                    -> keep sorted structure / heap
   exponential recursion with repeats  -> DP / memoization
   "k-th", "top k"                     -> heap / quickselect
   linear search over sorted/monotone  -> binary search

1.6  PATTERN RECOGNITION: CLUE -> TECHNIQUE
==============================================================================

 CLUE IN THE PROBLEM                                  TRY
 --------------------------------------------------   --------------------------
 Pair/triplet with a target sum, array unsorted        Hash map
 Pair/triplet with a target sum, sorted/sortable       Two pointers (3Sum: sort + 2 ptr)
 Longest/shortest substring or subarray with a rule    Sliding window
 Subarray sum with negatives / count subarrays         Prefix sum + hash map
 Frequency, anagrams, duplicates, grouping             Hash map / Counter / set
 Palindromes, reverse, in-place partition              Two pointers
 Sorted array, search, "minimum such that ..."         Binary search (on index/answer)
 Next greater/smaller, histogram, temperatures         Monotonic stack
 Window max/min                                        Monotonic deque
 Top k / k-th / merge k / running median               Heap
 Tree: depth, paths, LCA, validate                     DFS recursion (return from children)
 Tree: level, shortest depth, views                    BFS with a queue
 Graph: connected components, cycles, islands          DFS/BFS/Union-Find
 Graph: fewest steps (unweighted)                      BFS (multi-source for grids)
 Graph: cheapest path non-negative weights             Dijkstra
 Dependencies / ordering / prerequisites               Topological sort
 Intervals: merge/overlap/rooms                        Sort by start (or end) + heap/sweep
 All combinations/permutations/subsets/board puzzles   Backtracking
 Max/min/count ways, overlapping choices               Dynamic programming
 Local choice provably optimal (schedule, jump)        Greedy
 Prefix/word dictionary queries, grid word search      Trie
 Single/missing/duplicate number, subsets of <= 20     XOR / bit manipulation / bitmask
 Linked list: middle, cycle, reverse, merge            Fast/slow pointers, dummy node
 Design (LRU, min stack, iterator, queue via stacks)   Hash map + DLL; auxiliary stack

 "The data is sorted" is almost always a hint. So is "k" (heap / window size /
 number of operations), "contiguous" (window/prefix), and "all possible" (backtracking).

1.7  ONLINE ASSESSMENTS (OA)
==============================================================================

 STRATEGY
   1) Skim all problems first; start with the one you can finish fastest.
   2) Read constraints; pick the complexity target (1.5).
   3) Run the sample tests, then write 3-4 of your own edge cases.
   4) PARTIAL CREDIT: if stuck, submit a correct brute force - hidden tests are
      usually split; small cases still score.
   5) Do not spend more than ~1/3 of the total time on one problem without a
      working solution.
   6) Keep the last 5-10 minutes for re-checks (off-by-one, printing format).
   7) Don't copy/paste from outside sources; plagiarism detection and proctoring
      exist. Follow the rules (camera, tab switching).

 INPUT / OUTPUT BOILERPLATE (HackerRank-style stdin/stdout)
     import sys
     input = sys.stdin.readline          # much faster than input()
     n = int(input())
     arr = list(map(int, input().split()))
     s = input().strip()
     # many lines at once:
     data = sys.stdin.read().split()     # tokens
     # matrix:
     grid = [list(map(int, input().split())) for _ in range(r)]
     # output:
     print(" ".join(map(str, result)))    # single print for big outputs
     sys.stdout.write("\n".join(lines) + "\n")
   LeetCode-style: just implement the function in class Solution; no I/O.

 CODESIGNAL/CODILITY STYLE: function signature given; scoring shows correctness
 AND performance (time-limit tests with large n) - O(n^2) may pass correctness but
 fail performance.

 COMMON OA FAILURES: TLE from O(n^2); wrong answer on edge cases (n=1,
 duplicates, negatives); forgetting to handle multiple test cases; recursion
 limit; printing extra spaces/newlines; reading input slowly.

1.8  PYTHON SPEED TIPS FOR TIMED ROUNDS
==============================================================================

 WRITING SPEED (get the code down fast and correct)
   - Know the standard library cold:
        from collections import Counter, defaultdict, deque, OrderedDict
        import heapq, bisect, itertools, functools, math, sys
        from functools import lru_cache, cache
        from itertools import permutations, combinations, product, accumulate
   - Idioms to type from memory:
        a, b = b, a                       swap
        for i, x in enumerate(arr):       index + value
        for a, b in zip(x, y):            parallel loop
        sorted(arr, key=lambda t: (t[0], -t[1]))
        Counter(s).most_common(k)
        d = defaultdict(list); d[k].append(v)
        dirs = [(1,0),(-1,0),(0,1),(0,-1)]
        float('inf'), -float('inf')
        arr[::-1]    "".join(parts)    divmod(a, b)    max(arr, default=0)
        heapq.heappush(h, (cost, node))   negate for max-heap
        bisect.bisect_left(a, x)
        prefix = list(accumulate(arr, initial=0))
        2D list: [[0]*m for _ in range(n)]
        any(...)   all(...)   sum(1 for x in a if cond)

 RUN-TIME SPEED (pure Python is slow)
   - Prefer built-ins and comprehensions over manual loops (C speed).
   - Avoid recursion for depth > ~1000 or in hot paths: iterate / explicit stack.
   - Use sets/dicts for membership, not lists.
   - Use deque (not list.pop(0)) for queues.
   - Avoid repeated slicing (copies) and string += in loops; use join.
   - Cache attribute lookups in hot loops (append = res.append).
   - Use local variables rather than globals inside functions.
   - Precompute (prefix sums, sorted copies, factorials) once.
   - heapify(list) instead of n pushes; sort once instead of repeatedly.
   - sys.stdin for large input; print once.
   - @lru_cache for memoization (arguments hashable).
   - If still too slow: restructure the algorithm (complexity win beats micro-
     optimisation), or use numpy only if allowed.
   - sys.setrecursionlimit(10**6) only as a last resort (stack crash risk).

==============================================================================
1.9  TESTING AND DEBUGGING UNDER PRESSURE
==============================================================================

 AFTER CODING (always, even if you "know" it works):
   1) DRY-RUN the given example line by line, writing variable values.
   2) Test EDGE CASES (use this checklist):
        - empty input / n = 0          - single element
        - two elements                 - all elements equal
        - already sorted / reverse sorted
        - duplicates                   - negative numbers / zeros
        - maximum size (performance)   - target at the first/last position
        - no valid answer              - overlapping / touching boundaries
        - strings: empty, one char, all same, spaces, case differences
        - trees: empty, single node, skewed; graphs: disconnected, cycle,
          self-loop
   3) Check loop bounds (off-by-one): range(n) vs range(n-1) vs n+1, <= vs <.
   4) Check initial values (inf / -inf / 0 / None) and return for "not found".
   5) Re-read the problem statement for requirements you skipped (return type,
      0- or 1-indexed, stable order).

 DEBUGGING TECHNIQUE
   - Narrow down: print intermediate state on the smallest failing input.
   - Compare with your brute force (differential testing) when time permits.
   - Check for mutation of shared objects (list aliasing, default arguments,
     [[0]*m]*n, recording path instead of path[:]).
   - Integer vs float division (// vs /); string vs int types.
   - Infinite loop? Verify that every iteration makes progress.
   - RecursionError? Missing base case or too deep.

 TYPICAL BUG LIST (check these first)
   off-by-one | wrong initial value | not handling empty | modifying list while
   iterating | forgetting to update pointer | using = instead of == | wrong
   variable in nested loop | shadowed names | forgetting to return | KeyError on
   missing key (use .get / defaultdict) | IndexError on i+1 / i-1.

==============================================================================
1.10  WHAT TO DO WHEN STUCK
==============================================================================

   1) Re-read the problem and constraints; restate it in your own words.
   2) Solve a SMALLER or SIMPLER version (n=2, 3). Draw it.
   3) Brute force first: even a slow solution reveals structure.
   4) Ask "what am I recomputing?" (-> memoize/prefix/hash) and "what is
      searched repeatedly?" (-> sort/binary search/hash).
   5) Look at the output: can I build it from the previous answer (DP)? Is it
      about ordering (sort)? About connections (graph)?
   6) Try the toolbox in order: sort / hash map / two pointers / window / stack /
      heap / binary search / DFS-BFS / DP / greedy / backtracking.
   7) Change the representation: index <-> value, array <-> prefix array,
      matrix <-> graph, forward <-> reverse direction.
   8) Think about invariants: "what is true at every step?"
   9) Say your thoughts aloud and ask for a hint - hints are normal; silence is
      not.
   10) Never go silent for more than ~1 minute.

==============================================================================
1.11  COMMUNICATION SCRIPT (THINK ALOUD)
==============================================================================

   Understanding : "So the input is ... and I need to return ... Let me confirm
                    with an example ..."
   Questions     : "Can the array contain duplicates / negatives?"
   Brute force   : "A straightforward approach is ... which is O(n^2) time, O(1)
                    space."
   Insight       : "The bottleneck is the inner search. If I store seen values in
                    a hash map I can do that lookup in O(1)."
   Trade-off     : "That costs O(n) extra space. If memory is tight I could sort
                    and use two pointers for O(n log n) time and O(1) space."
   Plan          : "I'll iterate once, for each x check target - x, then insert x."
   Coding        : narrate non-trivial lines; name variables well.
   Testing       : "Let me trace [2,7,11,15] with target 9 ... Now edge cases:
                    empty array, duplicates like [3,3] with target 6 ..."
   Wrap-up       : "Time O(n), space O(n). I could extend this to return all pairs
                    by ..."
   Tone: collaborative, calm; welcome hints; admit mistakes and fix them.

1.12  WORKED TIMED WALKTHROUGH: SUBARRAY SUM EQUALS K  (target: 25 min)
==============================================================================

 PROBLEM: Given an integer array nums (may contain negatives) and an integer k,
 return the number of contiguous subarrays whose sum equals k.
 Example: nums = [1,2,3], k = 3  ->  2   ([1,2] and [3]).

 0:00-0:03  UNDERSTAND/CLARIFY
    - Contiguous, count them (not list them). Negatives allowed? Yes -> sliding
      window will NOT work. n up to ~2*10^4 / 10^5? Assume 10^5 -> need O(n) or
      O(n log n).
 0:03-0:06  EXAMPLE BY HAND
    - [1,2,3]: subarrays: [1]=1, [1,2]=3 *, [1,2,3]=6, [2]=2, [2,3]=5, [3]=3 *.
      Answer 2. Edge: empty array -> 0; k = 0 with zeros [0,0] -> 3 subarrays.
 0:06-0:09  BRUTE FORCE: for every start i, extend end j keeping a running sum;
            count when sum == k. O(n^2) time, O(1) space.
            # HOW: for each of the n starts the inner loop extends over up to n ends: n(n+1)/2 pairs -> O(n^2); only a running sum -> O(1) space.
 0:09-0:14  OPTIMISE (find the bottleneck: for each end we re-scan all starts)
    - Let P[j] = sum of nums[0..j-1]. A subarray (i..j-1) sums to k  <=>
      P[j] - P[i] = k  <=>  P[i] = P[j] - k.
    - So at each j, count how many EARLIER prefix sums equal P[j] - k: a hash map
      of prefix-sum frequencies. Seed it with {0: 1} for subarrays starting at
      index 0.
      Why not sliding window? Negatives break monotonicity.
    - Complexity: O(n) time, O(n) space.
    # HOW: one pass of n steps, each an O(1)-average dict get/set; the dict holds at most n+1 distinct prefix sums -> O(n) space.
 0:14-0:20  CODE
      def subarray_sum(nums, k):
          counts = {0: 1}          # prefix sum 0 occurs once (empty prefix)
          prefix = answer = 0
          for x in nums:
              prefix += x
              answer += counts.get(prefix - k, 0)
              counts[prefix] = counts.get(prefix, 0) + 1
          return answer
 0:20-0:25  TEST
    - [1,2,3], k=3: prefix 1 (need -2: 0) counts{0:1,1:1}; prefix 3 (need 0: 1)
      answer 1, counts{...,3:1}; prefix 6 (need 3: 1) answer 2.  -> 2  OK.
    - [1,-1,0], k=0: prefix 1 (need 1: 0); prefix 0 (need 0: 1) ans 1, counts[0]=2;
      prefix 0 (need 0: 2) ans 3 -> subarrays [1,-1], [0], [1,-1,0] = 3  OK.
    - Empty list -> 0 OK. All zeros [0,0,0], k=0 -> 6.
 0:25  WRAP-UP: O(n) time/space; update the map AFTER the lookup so an empty
       subarray isn't counted when k = 0; follow-up: "subarray sum divisible by
       k" uses prefix % k; "2D version" uses 2D prefix sums.

1.14  PREPARATION PLAN, PRACTICE RULES, SELF-RUBRIC
==============================================================================

 8-WEEK PLAN (about 1-2 hours/day; adjust to your timeline)
   Week 1 : Complexity analysis, arrays, strings, hash tables
   Week 2 : Two pointers, sliding window, prefix sums, sorting & binary search
   Week 3 : Linked lists, stacks, queues, monotonic stack/deque
   Week 4 : Trees, BST, heaps / priority queues
   Week 5 : Graphs (BFS, DFS, Dijkstra, Union-Find, topological sort)
   Week 6 : Recursion, backtracking, greedy
   Week 7 : Dynamic programming (1D -> 2D -> knapsack -> strings)
   Week 8 : Tries, bits, mixed timed mocks, weak-area review

 4-WEEK CRASH PLAN: Week 1 arrays/hashing/pointers/window; Week 2 stacks, lists,
   trees, heaps; Week 3 graphs, backtracking, DP basics; Week 4 mocks + review.

==============================================================================
2.1  RECAP
==============================================================================

 TIME complexity = how the NUMBER OF BASIC OPERATIONS grows with input size n.
 SPACE complexity = how the EXTRA MEMORY grows with n (auxiliary space; mention if
 you include the input or the output).

 NOTATIONS
   O(g)  upper bound (at most, grows no faster than g) - the default in interviews
   Omega(g) lower bound (at least)
   Theta(g) tight bound (both)
 Rules: drop constants (O(2n)=O(n)), drop lower-order terms (O(n^2+n)=O(n^2)),
 sequential steps ADD, nested steps MULTIPLY, different inputs get different
 variables (O(a*b), O(a+b)), log base is irrelevant.

 ORDER:  1 < log n < sqrt(n) < n < n log n < n^2 < n^3 < 2^n < n! < n^n

 CASES: best / average / worst. Quote the WORST case unless asked; mention the
 average when it differs (quicksort, hash tables). AMORTIZED: average cost per
 operation over a worst-case sequence (list.append).

==============================================================================
2.2  STEP-BY-STEP METHOD TO ANALYSE ANY CODE
==============================================================================

    1) NAME THE INPUT SIZES: n (array length), m (second array), V and E (graph),
       R and C (grid), L (string length), k (parameter).
    2) FIND THE DOMINANT OPERATIONS: loops, recursive calls, library calls.
    3) COUNT HOW MANY TIMES each runs, as a function of the sizes:
         - sequential blocks -> add
         - nested blocks -> multiply (careful: dependent bounds -> sum a series)
         - recursion -> write a recurrence (2.4)
    4) ADD HIDDEN COSTS of built-ins: slicing, `in` on a list, sort, string
       concatenation, copying (2.5).
    5) SIMPLIFY: keep the dominant term, drop constants.
    6) SPACE: variables (O(1)), new containers (their size), recursion depth,
       output size (state if it is counted).
    7) SANITY CHECK with tiny n and with extreme cases (best vs worst case).

 SHORT RECIPE: "How many times does the innermost statement run?"

 DIAGRAM - nested loop with dependent bound:
      i=0: j runs 0 times   *
      i=1: j runs 1 time    * *
      i=2: j runs 2 times   * * *
      ...
      i=n-1:                * * * ... *        total = 0+1+...+(n-1) = n(n-1)/2
                                                -> O(n^2) (a triangle, not a square)

==============================================================================
2.3  LOOP PATTERNS -> COMPLEXITY
==============================================================================

 PATTERN                                                    TIME
 for i in range(n): O(1)                                    O(n)
 for i in range(0, n, k): O(1)  (k constant)                O(n)
 i = 1; while i < n: i *= 2    (or n //= 2)                 O(log n)
 for i in range(n): for j in range(n)                       O(n^2)
 for i in range(n): for j in range(i)  (triangle)           O(n^2)
 for i in range(n): for j in range(m)                       O(n*m)
 for i in range(n): j = 1; while j < n: j *= 2              O(n log n)
 for i in range(1, n+1): for j in range(0, n, i)  (harmonic) O(n log n)
 i = 1; while i < n: for j in range(i): ...; i *= 2         O(n)   (1+2+4+...+n/2)
 while n: for i in range(n): ...; n //= 2                   O(n)   (n + n/2 + ...)
 i = 0; while i*i <= n: i += 1                               O(sqrt n)
 two pointers, each moves forward at most n times            O(n)
 while loop with inner while where inner index never resets  O(n) amortized
 3 nested loops                                              O(n^3)
 loop over subsets: for mask in range(1<<n): for i in range(n)  O(n * 2^n)
 loop with break: analyse the worst case                     (may be O(1) best)
 # HOW (loop table): each row = (iterations of the outer loop) x (work per iteration). Halving/doubling loops take log2(n) iterations; nested loops multiply;
 #      a loop whose inner work grows/shrinks geometrically sums to a constant multiple of n; two pointers that never move back total <= 2n steps.

 GEOMETRIC vs ARITHMETIC SUMS (frequent trap)
    1 + 2 + 3 + ... + n         = n(n+1)/2     -> O(n^2)
    1 + 2 + 4 + 8 + ... + n     = 2n - 1       -> O(n)     (geometric, dominated by the last term)
    n + n/2 + n/4 + ... + 1     <= 2n          -> O(n)
    log n + log n + ... (n times)               -> O(n log n)
    1 + 1/2 + 1/3 + ... + 1/n  ~ ln n          -> n*(that) = O(n log n)
    # HOW: arithmetic series 1+...+n = n(n+1)/2 ~ n^2/2. Geometric series with ratio 2: the last term n is bigger than all the earlier ones combined
    #      (1+2+...+n/2 = n-1), so the sum is ~2n. Harmonic series 1+1/2+...+1/n ~ ln n.

==============================================================================
2.4  RECURSION -> COMPLEXITY
==============================================================================

 METHOD:
   1) Write the recurrence T(n) = (#calls) * T(size of each) + work outside calls.
   2) Solve: unrolling, recursion tree, or Master theorem.

 MASTER THEOREM  T(n) = a T(n/b) + O(n^d)
    compare d with log_b(a):
       d <  log_b a  ->  O(n^(log_b a))      (leaves dominate)
       d == log_b a  ->  O(n^d log n)        (every level equal)
       d >  log_b a  ->  O(n^d)              (root dominates)

 QUICK TABLE
    T(n) = T(n-1) + O(1)           O(n)               linear recursion
    T(n) = T(n-1) + O(n)           O(n^2)
    T(n) = 2 T(n-1) + O(1)         O(2^n)             subsets, hanoi, naive fib-like
    T(n) = T(n-1) + T(n-2) + O(1)  O(1.618^n) ~ O(2^n)
    T(n) = T(n/2) + O(1)           O(log n)           binary search
    T(n) = T(n/2) + O(n)           O(n)               quickselect (average)
    T(n) = 2T(n/2) + O(1)          O(n)               tree traversal
    T(n) = 2T(n/2) + O(n)          O(n log n)         merge sort
    T(n) = 3T(n/2) + O(n)          O(n^1.585)         Karatsuba
    T(n) = k T(n-1)                O(k^n)             branching backtracking
    # HOW: the Master theorem compares the work at the root (n^d) with the number of leaves (n^(log_b a)). The bigger one dominates;
    #      a tie means every level costs the same and there are log n levels -> extra log n factor.

 CALL-TREE VIEW (fast for interviews):
    total work = (number of calls) x (work per call)
    number of calls ~ branching^depth
      fib(n): branching 2, depth n -> ~2^n calls
      permutations of n: n * (n-1) * ... = n! leaves
      subsets: 2^n leaves
      memoized: number of DISTINCT states x work per state

 RECURSION SPACE = maximum DEPTH (stack frames), not the number of calls.
    factorial O(n) | naive fib O(n) | binary search O(log n) |
    DFS on graph O(V) | merge sort O(log n) stack + O(n) buffer |
    quick sort O(log n) average stack, O(n) worst | tree DFS O(height).

 DP: time = (number of states) x (transitions per state); space = table size
 (often reducible to a row or O(1)).
    1D DP O(n) | 2D DP (n x m) O(nm) | knapsack O(nW) | interval DP O(n^3) |
    bitmask DP O(2^n * n).
    # HOW: DP time = (number of table cells) x (work per cell); space = table size, or one row if only the previous row is needed.

==============================================================================
2.6  AMORTIZED ANALYSIS IN PRACTICE
==============================================================================

 Idea: a few operations are expensive, but the TOTAL over a sequence is small, so
 the cost per operation averaged over the sequence is low.

 EXAMPLES
   - list.append (dynamic array): resizing copies n items occasionally; total for
     n appends <= ~3n -> O(1) amortized.
   - Two pointers / sliding window: inner `while` looks like nested loops, but
     each pointer moves at most n times in total -> O(n), NOT O(n^2).
   - Monotonic stack/deque: each element is pushed once and popped at most once ->
     O(n) total even with a `while` inside the `for`.
   - Union-Find with path compression + rank: ~O(alpha(n)) per operation.
   - Hash table rehashing: amortized O(1) insert.
   - Queue from two stacks: each item moves at most twice -> O(1) amortized.
   - Binary counter increment: O(1) amortized (total flips <= 2n for n increments).
   - Kadane / prefix sums: single pass.

 HOW TO ARGUE: "Each element enters the structure once and leaves once, so the
 total work across the whole loop is O(n)." (Aggregate method.)

 AVERAGE-CASE vs AMORTIZED: average case uses probabilities over inputs;
 amortized is a worst-case guarantee over a sequence of operations.

2.7  SPACE COMPLEXITY: WHAT COUNTS
==============================================================================

   - AUXILIARY space = extra memory beyond the input (most common meaning).
   - Total space = input + auxiliary. Say which one you give.
   - Count: new lists/dicts/sets/strings, copies/slices, recursion stack depth,
     memo tables, queues/stacks/heaps in BFS/DFS, output if you built it.
   - "In-place" = O(1) auxiliary (sometimes O(log n) accepted).

 EXAMPLES
   reverse in place two pointers      O(1)      reverse by creating a new list   O(n)
   hash map of n items                O(n)      counting lowercase letters       O(26) = O(1)
   BFS on grid R x C                  O(R*C)    DFS recursion on grid            O(R*C) worst
   recursive tree DFS                 O(h)      iterative tree DFS               O(h)
   merge sort                         O(n)      heap sort                        O(1)
   all subsets stored                 O(n*2^n)  subsets recursion only           O(n)
   2D DP table                        O(nm)     rolling array                    O(min(n,m))
   Python: arr[1:] in recursion       O(n) per frame -> O(n^2) total!

 TIME-SPACE TRADE-OFFS (be ready to discuss):
   Two Sum: O(n^2)/O(1)  vs  hash map O(n)/O(n)  vs  sort+two pointers O(n log n)/O(1)
   Fibonacci: recursion O(2^n)/O(n)  vs  memo O(n)/O(n)  vs  loop O(n)/O(1)
   Duplicates: nested loops O(n^2)/O(1)  vs  sort O(n log n)  vs  set O(n)/O(n)
   Range sum queries: recompute O(n) each  vs  prefix sums O(1) each after O(n)
   # HOW: Two Sum brute force = n(n-1)/2 pairs; hash map = n lookups + up to n stored; sort = n log n + two-pointer scan n. Fibonacci: naive ~2^n calls;
   #      memo = n states; loop = n steps with 2 variables. Prefix sums: n additions once, then each query is one subtraction.

==============================================================================
2.10  OPTIMISATION LADDER: FROM BRUTE FORCE TO OPTIMAL
==============================================================================

 Show this progression in interviews (state complexity at each rung):

  PROBLEM: "Does the array contain two numbers adding to target?"
     Rung 1  brute force, all pairs               O(n^2) time   O(1) space
     Rung 2  sort + two pointers                  O(n log n)    O(1)
     Rung 3  hash set of seen values              O(n)          O(n)
     (Optimal in time: must read all input -> Omega(n).)

  PROBLEM: "Longest substring without repeating characters"
     Rung 1  all substrings + check               O(n^3)
     Rung 2  for each start extend until repeat   O(n^2)
     Rung 3  sliding window + set                 O(n)  (each char added/removed once)
     Rung 4  window + last-index map (jump left)  O(n), fewer steps

  PROBLEM: "Fibonacci"
     naive recursion O(2^n) -> memoization O(n) time/space -> loop O(n)/O(1) ->
     matrix power / fast doubling O(log n).

  PROBLEM: "Maximum subarray sum"
     O(n^3) all subarrays -> O(n^2) running sums -> O(n log n) divide & conquer ->
     O(n) Kadane.

  PROBLEM: "k-th largest element"
     sort everything O(n log n) -> min-heap of size k O(n log k) ->
     quickselect O(n) average.

  GENERAL RUNGS: brute force -> remove repeated work (memo / prefix / hash) ->
  exploit order (sort / binary search / two pointers) -> exploit structure (heap /
  DP / greedy) -> reduce space (rolling variables / in place).

==============================================================================
2.11  LOWER BOUNDS AND "CAN WE DO BETTER?"
==============================================================================

 - ANY algorithm that must READ all n inputs is Omega(n). So O(n) time is optimal
   for scanning problems (max, sum, duplicates by hashing).
 - Comparison-based SORTING is Omega(n log n) (decision tree with n! leaves).
 - SEARCHING a sorted array by comparisons is Omega(log n); unsorted is Omega(n).
 - Printing/returning all subsets/permutations is Omega(output size) (2^n, n!).
 - Element distinctness needs Omega(n log n) in the comparison model (O(n) with
   hashing, which is a different model).
 - Merging two sorted lists of sizes m, n: Omega(m + n) (every element must be
   output).
 - Space: if you must return n items, output alone is O(n).

 WHEN THE INTERVIEWER ASKS "CAN YOU DO BETTER?"
   1) Check the lower bound: am I already at Omega(input)? If yes, say so.
   2) Otherwise identify the bottleneck term in your complexity.
   3) Ask what information is unused (sortedness? bounded range? duplicates?).
   4) Trade space for time (hash/memo/precompute) or time for space (sort in place).

==============================================================================
2.12  ESTIMATING REAL RUNNING TIME
==============================================================================

   operations = f(n) from your analysis (e.g. n log n)
   time ~ operations / speed
   speed (CPython simple ops): ~10^6-10^7 / s for Python-level loops;
                               built-ins (sort, sum, set ops) ~10^7-10^8 elements/s.

   Examples with n = 10^5:
      O(n log n) = 1.7 x 10^6 ops   ->  well under a second
      O(n^2)     = 10^10 ops        ->  hours in Python -> reject
   n = 10^6: O(n) loop ~ 0.1-0.5 s fine; O(n log n) with Python-level heap ~ several
   seconds (borderline).

   Constant factors matter at the margin: a Python-level O(n log n) heap loop can be
   slower than a built-in sort-based O(n log n); recursion is slower than loops;
   dict/set ops ~ 50-100 ns each.

   Memory: a Python int in a list costs ~28 bytes + 8 byte pointer; a list of 10^7
   ints ~ 360 MB-ish. Prefer arrays/bitsets/numpy only when allowed; avoid
   storing what you can compute.

==============================================================================
2.13  HOW TO STATE COMPLEXITY IN AN INTERVIEW
==============================================================================

 TEMPLATE:
   "Let n be the length of the array. I iterate once, and each hash-map operation
    is O(1) on average, so the time is O(n). The map can hold up to n entries, so
    the extra space is O(n)."

 INCLUDE:
   - the variables you use (n, m, V, E, k, L),
   - the dominant step and WHY (sorting dominates -> O(n log n)),
   - average vs worst case when they differ ("hash lookups are O(1) on average,
     O(n) worst case"),
   - amortized claims with the justification ("each element is pushed and popped
     once"),
   - space split: auxiliary vs output; recursion stack,
   - trade-offs and alternatives.

 AVOID: saying O(n) when two inputs exist; forgetting sort cost; claiming O(1)
 space while using recursion; hiding slicing/concatenation costs; "log n" without
 saying what halves.

 DATA STRUCTURES (average / worst where different)
   Structure          Access   Search    Insert        Delete        Notes
   Array/list         O(1)     O(n)      O(n) (end O(1)am) O(n)      contiguous
   Linked list        O(n)     O(n)      O(1) at node/head O(1) at node  no random access
   Stack / queue      -        O(n)      O(1)          O(1)          LIFO / FIFO

   Hash table         -        O(1)/O(n) O(1)/O(n)     O(1)/O(n)     unordered
   BST (balanced)     -        O(log n)  O(log n)      O(log n)      sorted order
   BST (skewed)       -        O(n)      O(n)          O(n)
   Binary heap        min O(1) O(n)      O(log n)      O(log n)      build O(n)
   Trie               -        O(L)      O(L)          O(L)          prefix queries
   Graph adj. list    -        O(V+E) traversal         edge add O(1)
   Union-Find         -        ~O(1)     union ~O(1)
   # HOW: array access = address math (O(1)), shifting for insert/delete (O(n)); linked list = pointer walk to access (O(n)), rewiring to insert (O(1));
   #      hash = jump to a bucket; BST = one root-to-leaf path = height; heap = height log n; trie = one hop per character.

 SORTING
   Bubble/Selection/Insertion O(n^2) | Merge, Heap O(n log n) | Quick avg
   O(n log n), worst O(n^2) | Counting O(n+k) | Radix O(d(n+b)) | Timsort O(n) best,
   O(n log n) worst. Stable: bubble, insertion, merge, counting, radix, Timsort.

 SEARCHING
   Linear O(n) | Binary O(log n) | Hash O(1) avg | BFS/DFS O(V+E).

 GRAPH ALGORITHMS
   BFS/DFS/Topo O(V+E) | Dijkstra O((V+E) log V) | Bellman-Ford O(VE) |
   Floyd O(V^3) | Kruskal O(E log E) | Prim O(E log V).

 PYTHON BUILT-INS: see 2.5.

 FORMULAS TO KNOW
   1+...+n = n(n+1)/2 | 1+2+4+...+2^k = 2^(k+1)-1 | log2(n!) = Theta(n log n) |
   subsets 2^n | permutations n! | combinations C(n,k) | Catalan C(2n,n)/(n+1) |
   height of a complete tree floor(log2 n) | tree with n nodes has n-1 edges.


==============================================================================
 4.  COMMON MISTAKES
==============================================================================

 TIMED ROUNDS
   - Coding immediately without understanding or clarifying.
   - Going silent; not explaining the idea.
   - Jumping to a clever solution without stating the brute force.
   - Over-engineering; writing too much code; no helper functions.
   - Ignoring constraints (writing O(n^2) for n = 10^5).
   - Not testing; only running the happy path; not dry-running.
   - Panicking after one bug; random changes instead of tracing.
   - Spending 30 minutes on one OA problem; no partial submission.
   - Not reading the problem statement completely (return type, indexing, ties).
   - Not stating complexity at the end.
   - Memorising solutions instead of patterns (fails on variations).
   - Reading input slowly in Python (input() in a loop of 10^6 lines).

 COMPLEXITY ANALYSIS
   - Multiplying instead of adding sequential loops; adding instead of
     multiplying nested ones.
   - Treating independent inputs as one n.
   - Missing hidden costs: slicing, `in` on lists, string concatenation, sort in a
     loop, deepcopy.
   - Saying hash operations are always O(1).
   - Counting recursive calls as space (space = depth).
   - Calling inner `while` loops O(n) each when pointers only move forward
     (amortized O(n) total).
   - Calling the naive Fibonacci's space O(2^n).
   - Forgetting the recursion stack in "O(1) space" claims.
   - Confusing O(n log n) with O(n) for heapify, or log n with n for halving + copy.
   - Reporting best case as the complexity.
   - Ignoring output size (e.g., generating all subsets in O(2^n) when each costs
     O(n) to copy).
   - Equating "fast in practice" with a better big-O.


==============================================================================
 5.  INTERVIEW FAQs
==============================================================================

 Q1.  How should I start a coding interview problem?
      Restate the problem, ask clarifying questions, walk through an example, then
      outline brute force before optimising.
 Q2.  What if I don't know the solution?
      Say what you do know, solve a simpler version, state the brute force, and
      ask for a hint. Interviewers evaluate the process.
 Q3.  Should I write the brute force?
      State it with its complexity; code it only if time is plentiful, the
      interviewer asks, or in an OA to secure partial credit.
 Q4.  How much should I talk?
      Continuously but concisely: intent before each block of code, not every
      keystroke.
 Q5.  How do I choose between hash map and sorting?
      Hash map: O(n) time/O(n) space, keeps original order and indices. Sorting:
      O(n log n), O(1) extra, loses indices unless stored.
 Q6.  How do I handle a bug in the interview?
      Stay calm, trace with the failing input, find the first wrong value, fix,
      re-run.
 Q7.  Can I use built-in functions (sort, Counter, heapq)?
      Usually yes; say what they cost. If the question is about implementing the
      algorithm itself (e.g. sort), don't use the built-in.
 Q8.  What is the difference between time complexity and running time?
      Complexity describes growth with input size, independent of hardware;
      running time is the actual measured seconds.
 Q9.  Why do we ignore constants?
      For large n the growth rate dominates; constants depend on the machine and
      implementation. (But mention them when comparing same-order approaches.)
 Q10. Is O(n log n) always better than O(n^2)?
      Asymptotically yes; for tiny n the quadratic algorithm with a smaller
      constant can be faster (insertion sort inside Timsort).
 Q11. What is the complexity of recursion with memoization?
      (distinct states) x (work per state).
 Q12. How do I know when to stop optimising?
      When you reach the lower bound (e.g. must read all input) or meet the
      constraints with margin; confirm with the interviewer.
 Q13. How many problems should I solve?
      Roughly 150-250 chosen by pattern with deep understanding and spaced
      review beats hundreds of skimmed ones.
 Q14. How do I manage time in an OA?
      Skim, easiest first, partial credit with brute force, leave the final 5-10
      minutes for checks.
 Q15. What's the best way to practise?
      Timed, pattern-grouped, then mixed; explain aloud; re-solve failures a week
      later; keep a mistake log.
 Q16. What do I do if I finish early?
      Test more edge cases, discuss complexity and trade-offs, propose follow-ups
      (streaming input, larger scale, parallelism).
 Q17. What about whiteboard coding without an interpreter?
      Write neat code, use meaningful names, leave space for edits, and dry-run
      by hand on an example.
 Q18. How do I analyse complexity of a recursive function quickly?
      Number of calls x work per call; or recurrence + Master theorem; space =
      depth.

==============================================================================
 7.  QUICK REVISION SUMMARY
==============================================================================

 TIMED ROUNDS
   - Time split (45 min): 5 clarify | 5 example/approach | 5 brute force + optimise
     | 20 code | 7 test | 3 wrap-up.
   - Framework: Understand -> Match -> Plan -> Implement -> Review -> Evaluate.
   - Constraints decide the algorithm (n <= 10^5 -> O(n log n); n <= 2000 -> O(n^2);
     n <= 20 -> O(2^n); n <= 10 -> O(n!)). In Python, budget ~10^7 simple ops/sec.
   - Brute force first (state complexity), find the bottleneck, apply a pattern.
   - Clarify, think aloud, test edge cases, state final complexity.
   - OA: skim, easiest first, partial credit, fast I/O (sys.stdin), 5-10 min to
     re-check.
   - Stuck? simplify, example, brute force, ask what is repeated/searched, ask for
     a hint.
   - Practise timed, by pattern, with a mistake log and spaced repetition.

 COMPLEXITY ANALYSIS
   - Name the sizes -> count the innermost statement -> add hidden costs ->
     simplify -> space (variables + new containers + stack + output).
   - Sequential add, nested multiply, dependent loops sum a series, geometric
     sums stay O(n), harmonic sums give n log n.
   - Recursion: calls x work per call; recurrence/Master theorem; space = depth.
   - Python hidden costs: slicing, `in list`, string +=, insert/pop(0), sort in
     loops, deepcopy; hash ops O(1) average.
   - Amortized: two pointers, monotonic stack, dynamic array, DSU.
   - Lower bounds: must read input -> Omega(n); comparison sort -> Omega(n log n).
   - Always say: variables, dominant step, average vs worst, space, trade-offs.
